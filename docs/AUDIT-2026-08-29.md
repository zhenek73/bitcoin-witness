## 🔴 CRITICAL-1. Любой может доказать выдуманный факт о Bitcoin

**Где:** `contracts/asc/BitcoinFactVerifier.sol::_extractFact` + `contracts/evm/BitcoinWitnessReceiver.sol`.

`receiveUtxoFact` — `external` без ограничений (это осознанно и задокументировано в
комментарии: «Anyone can call this directly too — the value of the claim comes from
Attestcoin proving *who* called it»).

Но верификатор **не проверяет, кто вызвал**. В `_extractFact` есть четыре проверки:

```solidity
require(to == expectedEmitter,  ...);   // транзакция шла в наш контракт
if (log.addr != expectedEmitter) continue;   // событие из нашего контракта
if (log.topics.length != 3 || log.topics[0] != EVENT_SIGNATURE) continue;
require(status == 1, ...);
```

`log.topics[2]` — это индексированный `relayer` (то самое «кто»). Он **читается, но
никогда не сравнивается ни с чем**.

**Эксплойт целиком:**
1. Атакующий с любого EOA на exSat EVM вызывает
   `BitcoinWitnessReceiver.receiveUtxoFact(0xdeadbeef…, 0, 2_100_000_000_000_000)`.
2. Контракт послушно эмитит `BitcoinUtxoAttested` — `log.addr` наш, сигнатура наша,
   `to` наш, `status == 1`.
3. Attestcoin честно аттестует эту транзакцию (она реальная).
4. `proveBitcoinFact` проходит все require и записывает в `provenUtxoValue`
   21 млн BTC на несуществующем UTXO.

Единственная настоящая проверка — чтение `utxomng.xsat` в нативном контракте — при
прямом вызове просто обходится стороной. Вся цепочка доверия держится на звене,
которое верификатор не смотрит.

**Тесты это не поймали, а закрепили.** В `test_verifier.py` happy path подаёт
`topics=[EVENT_SIG, TXID, bytes(32)]` — relayer равен нулевому адресу, и тест
считает это успехом. То есть «факт, отправленный никем» — эталонное поведение.

**Фикс (обязателен до сабмита):**

```solidity
address public immutable expectedRelayer;   // reserved EVM-адрес аккаунта btcwitness

constructor(uint64 _exsatChainKey, address _expectedEmitter, address _expectedRelayer) {
    ...
    expectedRelayer = _expectedRelayer;
}

// в цикле по логам, рядом с проверкой topics[0]:
if (log.topics[2] != bytes32(uint256(uint160(expectedRelayer)))) continue;
```

Плюс defence-in-depth на приёмнике: `require(msg.sender == RELAYER)` в
`receiveUtxoFact`. Проверка в верификаторе — несущая (переживает передеплой
приёмника), проверка в приёмнике — дешёвая и отсекает мусор в логах.

**Откуда взять `expectedRelayer`.** `evm.xsat::call(from, …)` подставляет
*reserved address* аккаунта: `0xbbbbbbbb` ‖ name_u64 (8 байт BE) ‖ 8 нулевых байт.
Для имени `btcwitness` это

```
0xbbbbbbbb3e51c7666ac600000000000000000000
```

(посчитано; при другом имени аккаунта пересчитать по той же формуле).
Негативный тест «чужой relayer → revert» добавить в `test_verifier.py` — сейчас
такого кейса нет.

## 🟠 HIGH-2. Нативному контракту нужен BTC на газ — этого нет ни в одной смете

**Где:** `contracts/native/DEPLOY.md` («RAM is the only meaningful cost»),
`docs/stream/DECISIONS.md` (17).

Запрос конфига `evm.xsat` на живом EOS RPC:

```json
{"chainid":7200, "token_contract":"btc.xsat", "gas_price":500000,
 "ingress_bridge_fee":"0.00000000 BTC", "ingress_gas_limit":28000}
```

Газовый токен exSat EVM — **BTC** (контракт `btc.xsat`), не EOS. Транзакция, которую
шлёт `relayutxo`, оплачивается из баланса reserved-адреса аккаунта `btcwitness`
**внутри exSat EVM**. При нулевом балансе первый же вызов упадёт по insufficient
funds — и упадёт он на EVM-стороне, то есть Antelope-транзакция может выглядеть
успешной, а события не будет.

Сумма смешная — 30 000 газа × 500 000 wei = 1.5·10¹⁰ wei ≈ **1.5 сатоши** на релей —
но она обязана быть > 0. Это отдельный шаг деплоя: завести BTC на exSat EVM
(`btc.xsat` transfer → `evm.xsat` с memo = reserved-адрес) до первого прогона.

Формулировка «нативная часть = обычная EOS-разработка, платим RAM/CPU в EOS» верна
ровно наполовину: EOS-ресурсы за нативный контракт + BTC-газ за EVM-хоп.
`DEPLOY.md` надо дополнить, иначе первый живой прогон встанет здесь.

## 🟠 HIGH-3. «Доказано» ≠ «не потрачено» — а именно это обещает proof of reserves

**Где:** `BitcoinFactVerifier` — `provenUtxoValue` / `isProven`.

Хранится `(txid, index) -> value` и булев флаг. Высота `height` попадает в событие,
но **не в стораж**. Значит потребитель, читающий `getProvenValue`, не может отличить
UTXO, доказанный минуту назад, от доказанного на аттестации полугодовой давности —
а UTXO с тех пор мог быть потрачен. Повторный `proveBitcoinFact` со старым payload
просто перезапишет то же значение, ничего не освежив.

Для заявленного юзкейса (proof of reserves) это ключевая семантика, а не мелочь.
Минимальный фикс — хранить высоту и время:

```solidity
struct ProvenFact { uint64 value; uint64 height; uint64 provenAt; bool proven; }
mapping(bytes32 => mapping(uint32 => ProvenFact)) public facts;
```

и в README честно писать: «доказано, что на высоте H exSat видел этот выход
непотраченным», а не «этот выход существует». V2 — релей факта *расхода*
из `utxomng.xsat` spent-истории, тогда флаг можно снимать.

## 🟡 MEDIUM-6. Порядок байт txid нигде не зафиксирован

`demo.ts::computeUtxoId` берёт `Buffer.from(txid,'hex')` без разворота и это
работает против живых данных — значит `utxomng.xsat` хранит txid в том же виде,
в каком его отдаёт RPC. Но `bytes32 txid`, который в итоге лежит на Creditcoin,
потребитель будет сравнивать со своим представлением, а Bitcoin традиционно
показывает txid в обратном порядке байт. Один абзац в `ARCHITECTURE.md` («txid —
это ровно те 32 байта, что хранит exSat; для отображения в mempool.space
развернуть») снимает целый класс будущих «доказательство не сходится».

## 🟡 MEDIUM-7. `gas_limit` — параметр вызывающего без пола и потолка

`relayutxo` принимает `gas_limit` и передаёт как есть. Слишком маленький → EVM-tx
отваливается, события нет, а Antelope-транзакция прошла. Верификатор такое
корректно отвергнет (`status != 1`), но диагностировать будет неприятно.
Достаточно `check(gas_limit >= 50000 && gas_limit <= 1000000, ...)` и дефолта в
DEPLOY.md.
